# SD021. Инверсия оси X цели перцепшна (кадр камеры)

## Проблема

1. **Как всплыло.** При приёмке F11 (SD020, слежение за целью) на стенде `pi@192.168.2.2` записан позитивный сценарий: человек стоит прямо перед роботом, робот в `AutoFollow` должен подъехать и встать перед ним. Бэг `f11_follow_20260904_182253` (все топики контура, 101 с) + видео `f11_run1.mp4`. По видео робот физически доехал до ног стоящего впереди человека — со стороны «следование работает».

2. **Что на самом деле не так.** Позу цели перцепшн (`person_perception`, топик `/perception/nearest_person`, поля `person.x/y`) отдаёт в кадре `base_footprint`, где по REP-103 ось `x` направлена **вперёд**, `y` — влево. Но в бэге при человеке **спереди** координата `x` стабильно **отрицательная**, то есть цель рапортуется как будто **позади** робота. Сырые сэмплы (человек по видео — перед роботом):
   - `x = −1.92, y = +0.55, range 2.00 → пеленг 164°`
   - `x = −0.89, y = +0.22, range 0.92 → пеленг 166°`
   - `x = −0.41, y = −0.14, range 0.43 → пеленг −161°` (у самых ног — всё ещё `x<0`)
   Пеленг `atan2(y, x)` держится около **±165°** вместо ожидаемых ~0°. Ось `y` (лево/право) при этом сохраняет знак — инверсия именно по **X** (форвард камеры маппится в `−x` базы), а не полный разворот на 180°.

3. **Где ломается.** `person_perception` переводит точку из кадра глубины в `base_footprint` через TF `depth_camera_link → base_footprint` (`transform_to_base`, `base_frame=base_footprint`, `depth_frame=depth_camera_link`). Значит переворот знака X приходит из **статической TF / экстринсик камеры** (URDF платформы — F07/SD007, либо калибровка крепления — F24/SD012), или из знака в геометрии перевода оптического кадра (`person_geometry.hpp`). Сам `person_perception` точку не «сочиняет» — он доверяет TF, поэтому чинить надо кадр/экстринсики камеры, а не ноду выбора ближайшего.

4. **Почему баг замаскирован «рабочим» видео.** Закон F11 берёт линейную скорость от `range` (всегда `≥ 0`) и всегда едет **вперёд**, а доворот считает от пеленга. Человек стоял ровно по курсу, поэтому «ехать вперёд» физически вело к нему — робот приблизился по счастливой геометрии, не по правильному управлению. Угловой канал при этом работал по ложному пеленгу ~165° (вместо истинных ~15°): вдали динамический лимит `ω_lim≈0` глушил доворот, вблизи давал резкий разворот. Для цели **сбоку** тот же баг увёл бы робота не туда — следование ненадёжно и верно лишь для цели строго по оси.

5. **Границы вины.** Сама реализация F11 (SD020) корректна и свою QA проходит: гейт `desired==vehicle` 2021/2021, `vehicle==hiwonder` 4041/4041, `stop_request` 0 %, заднего хода нет, насыщение трака 0 нарушений, закон против спеки `err=0.0000`. Нарушен **вход** F11 — контракт `I1` из [SD020/tech.md](../SD020/tech.md) «`x` вперёд, `y` влево в базе робота». Дефект общий для всех потребителей `/perception/*` (следование F11, будущая охрана столкновений F12, выбор ближайшего F08), а не только F11.

6. **Что надо починить.** Восстановить корректный кадр камеры так, чтобы человек **перед** роботом давал `x > 0` в `base_footprint` (REP-103): проверить и исправить знак/ориентацию оси X в TF `depth_camera_link` (URDF F07 и/или экстринсики F24/[SD012/measure.md](../SD012/measure.md)), при необходимости — знак в переводе оптического кадра в геометрии. Подтвердить, что `y` (лево/право) остаётся корректным. После фикса — перезаписать этот же позитивный бэг F11 и убедиться, что пеленг цели по курсу `→ 0`, а доворот включается штатно для цели сбоку.

## Решение

Восстановить корректный кадр цели перцепшна: человек **перед** роботом должен давать `x > 0` в `base_footprint` (REP-103: `x` вперёд, `y` влево), а не рапортоваться как «позади». Причина инверсии по X пока не локализована — она приходит из статической TF/экстринсиков камеры и может сидеть в одном из трёх мест: оптический joint в модели платформы (URDF F07), поза камеры из калибровочного файла на Pi (`t1ctl calib camera`, SD012), либо конвенция осей облака драйвера. Поэтому работа начинается с диагностики: снять **реальное** TF-дерево `depth_camera_link → base_footprint` со стенда/бэга, сопоставить сырой сэмпл облака с его позой в базе и указать пальцем на источник знака X. Затем — точечный фикс именно этого источника, без переписывания ноды выбора ближайшего (она точку не сочиняет, а доверяет TF). Ось `y` (лево/право) в бэге корректна — фикс не должен её сломать. Подтверждение — перезапись того же позитивного бэга F11 на стенде: цель по курсу даёт пеленг `→ 0`, доворот включается штатно для цели сбоку, следование ведёт к человеку по правильному управлению, а не по счастливой геометрии.

## Сценарии

### Позитивный
1. Инженер на стенде `pi@192.168.2.2` знает по приёмке F11 (бэг `f11_follow_20260904_182253`), что цель спереди рапортуется с `x<0` (пеленг ≈ ±165° вместо ~0°), и хочет вернуть кадру корректную ось X.
2. Инженер снимает по бэгу/со стенда реальное TF-дерево `depth_camera_link → base_footprint` и сопоставляет сырой сэмпл облака (точка на человеке спереди) с её позой в `base_footprint`.
   1. По расхождению локализуется источник знака X: оптический joint URDF, поза камеры из калибровочного файла SD012, либо конвенция осей облака драйвера.
3. Инженер вносит точечную поправку в найденный источник так, чтобы точка спереди давала `x > 0`, а знак `y` (лево/право) сохранился.
   1. Собранная модель/применённая калибровка даёт TF, в котором человек по курсу проецируется в `x>0, y≈0`.
4. Инженер перезаписывает тот же позитивный сценарий F11 на стенде (человек прямо перед роботом, `AutoFollow`).
   1. В новом бэге пеленг цели по курсу `atan2(y, x) → 0`, `x` цели спереди положителен, `y` сохраняет корректный знак лево/право.
   2. Угловой канал F11 включает доворот штатно; следование ведёт робота к человеку по правильному управлению.

### Негативный №1
1. Пункты позитивного сценария 1–2.
2. По снятому TF/сэмплу источник инверсии однозначно не локализуется (расхождение не сводится ни к одному из трёх кандидатов, либо знак `y` тоже нарушен — не чистая инверсия по X).
   1. Фикс не вносится вслепую. Диагностика фиксирует, что наблюдаемое расхождение не объясняется текущей гипотезой, и работа останавливается для уточнения — «примерно поправить знак» недопустимо.

### Негативный №2
1. Пункты позитивного сценария 1–3, фикс внесён.
2. При перезаписи бэга F11 пеленг по курсу к нулю не сходится, либо знак `y` (лево/право) после фикса инвертировался.
   1. Фикс считается неуспешным: коррекция по X не должна ломать ось Y и обязана давать пеленг `→0` для цели по курсу. Возврат к диагностике, а не приёмка «как есть».

## Функциональные требования
- Перцепшн должен отдавать позу цели в `base_footprint` по REP-103: человек **перед** роботом → `x > 0`; `y > 0` для цели слева, `y < 0` для цели справа.
- Пеленг цели по курсу `atan2(person.y, person.x)` должен быть близок к `0` для человека, стоящего прямо перед роботом (а не ≈ ±165°).
- Источник инверсии оси X должен быть локализован диагностикой (реальное TF-дерево `depth_camera_link → base_footprint` со стенда/бэга), а не предположён — фикс вносится в конкретно найденное место.
- Фикс не должен менять корректный знак оси `y` и не должен затрагивать логику выбора ближайшего (`person_perception` доверяет TF).
- Корректность кадра должна быть подтверждена перезаписью того же позитивного бэга F11 на стенде: пеленг цели по курсу `→ 0`, доворот F11 включается штатно.

## Нефункциональные требования
- Фикс локализуется в кадре/экстринсиках камеры (URDF F07, калибровочный файл SD012 или конвенция облака драйвера) — нода выбора ближайшего и закон управления F11 (SD020) не переписываются: их QA уже пройдена, вина — на входе.
- Дефект общий для всех потребителей `/perception/*` (следование F11, выбор ближайшего F08, будущая охрана столкновений F12); приёмка проводится на F11 как представителе — остальные потребители наследуют фикс кадра автоматически.
- Постоянный автотест-инвариант на «цель спереди → x>0» в рамках SD021 не вводится — достаточно однократного фикса с подтверждением бэгом.
- Проверка выполняется на реальном стенде `pi@192.168.2.2`; при изменении URDF требуется цикл сборка → деплой → перезапуск контура, при изменении калибровки — применение файла на Pi без пересборки.

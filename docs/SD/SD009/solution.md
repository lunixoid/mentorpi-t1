# SD009. Быстрый t1ctl

## Проблема
1. Команды `t1ctl`, которые печатают status (пустой вызов, `status`, `start`, `restart`, `stock`, `viewer status` / `viewer start`), ждут десятки секунд. Оператор прерывает `t1ctl status` через Ctrl+C.
2. После `start` / `restart` / `stock` CLI сначала переключает unit, затем снова гоняет полный status — ожидание удваивается. Обход — ждать или бросать команду.

## Решение
`t1ctl` отвечает оператору за приемлемое время: тот же kv-status, но без долгого сбора состояния по каждому топику и кадру по очереди. Неполная готовность сенсора — одна строка `degraded` без разбора причин. После `start` / `restart` / `stock` — короткое подтверждение, без повторного полного status.

## Сценарии

### Позитивный
1. Demo-контур на стенде, оператор проверяет состояние.
2. Оператор вызывает `t1ctl status` (или пустой `t1ctl`).
   1. За примерно 5 с печатается kv: demo / stock / chassis / mode / remote controller / lidar / camera / platform model / version.
   2. Если lidar / camera / model не полностью готовы — `degraded` одной строкой, без списка «нет цвета / нет TF / …».
3. Оператор вызывает `t1ctl start` / `restart` / `stock`.
   1. После переключения unit — короткое подтверждение без повторного полного status.
4. Оператор вызывает `t1ctl viewer status` или `viewer start`.
   1. Ответ в том же бюджете ожидания.

### Негативный №1
1. Пункты позитивного сценария №2.
2. Контейнер `mentorpi-t1` не running или demo failed.
   1. Status печатается быстро: demo failed/inactive, сенсоры inactive, без долгого ожидания ROS-сбора.

### Негативный №2
1. Пункты позитивного сценария №3.
2. `start` / `restart` / `stock` не удался.
   1. Короткое сообщение об ошибке без повторного полного status.

## Функциональные требования
- Должна быть возможность получить status теми же командами, что сейчас (`t1ctl`, `status`, viewer).
- Строки lidar / camera / platform model должны по-прежнему различать `active`, `degraded` и `inactive`.
- `degraded` должен печататься одной строкой, без адресных причин по каждому куску.
- После успешного `start` / `restart` / `stock` система должна подтвердить действие коротко, без повторного полного status.
- Отсутствие сенсора не должно маскироваться под `active`.

## Нефункциональные требования
- Ответ CLI, который сейчас печатает status, — примерно до 5 секунд (бюджет оператора).
- Сознательно не делаем: поштучные hints причин `degraded`.
- Версия CLI в этом изменении — 1.2.0.

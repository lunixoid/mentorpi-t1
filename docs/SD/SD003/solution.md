# SD003. Адаптер шасси (SIT)

## Проблема
1. Наш контур после питания жив, но на гусеницы не выходит: команды следования и стопа нечем довести до шасси, а `t1ctl` не показывает, живо ли шасси. Пока адаптера нет, «включил — следует» из каталога невозможно проверить на железе.
2. Обход: исходный образ Hiwonder и учебные игры, либо публикация в шасси в обход нашего контура. Оба пути дают два источника команд и ломают инвариант «по умолчанию стоит». Отдельно: нули в ROS-топиках сами по себе не доказывают, что гусеницы стоят.

## Решение
Единственная точка выхода нашего контура на гусеницы — адаптер шасси: команда с его входа становится движением, иначе робот физически стоит. Запрет движения (Forbidden), отсутствие команды, обрыв потока и отпускание управления дают стоянку. Нули в ROS (`Twist`, `MotorsState`) не считаются доказательством стоянки. В `t1ctl` честно виден статус шасси. Ручной пульт — отдельное изменение (SD004). По умолчанию робот стоит.

## Сценарии

### Позитивный
1. Наш контур запущен. Робот стоит. Нужно убедиться, что шасси управляется только через адаптер, и видеть, живо ли оно.
2. Оператор открывает `t1ctl`
   1. В статусе есть шасси: утилита берёт его из топика статуса шасси. Повторный запрос сразу после старта не показывает ложный `inactive`, если шасси живо
3. Оператор подаёт команду на вход адаптера (ручной пульт — SD004)
   1. Гусеницы едут согласно команде
4. Команда прекращается (отпускание, конец потока)
   1. Робот физически останавливается: гусеницы не вращаются, моторы не шумят в покое
5. Проверка окончена, ненулевых команд нет
   1. Робот стоит

### Негативный №1
1. Пункты позитивного сценария №1–2
2. Движение запрещено (Forbidden)
   1. Робот физически стоит, даже если на вход адаптера пришла ненулевая команда

### Негативный №2
1. Пункты позитивного сценария №1–3: робот ехал по команде на входе адаптера
2. Сообщения на входе адаптера пропали
   1. Робот физически останавливается

## Функциональные требования
- Должна быть возможность реально управлять гусеницами из нашего контура через единственную точку выхода — адаптер шасси
- Только адаптер владеет выходом на шасси `/hiwonder_controller/cmd_vel`; публикация `/cmd_vel` запрещена
- При ненулевой команде на входе адаптера и отсутствии Forbidden шасси должно двигаться
- При отсутствии команды на входе адаптера робот должен физически стоять
- В режиме Forbidden команда на шасси должна быть нулевой независимо от входа адаптера; робот должен физически стоять
- Если сообщения на входе адаптера прекратились, робот должен физически остановиться
- Нули в ROS (`Twist=0`, `MotorsState=0`) сами по себе не являются доказательством физической остановки
- По умолчанию, без команды на входе адаптера, робот должен стоять
- В `t1ctl` должен быть виден статус шасси (`chassis active` / `inactive`); утилита честно отражает наличие топика статуса, в том числе после холодного запуска
- Переключение пульта/джойстика в этом изменении не требуется (SD004)
- Реализуется только Forbidden; прочие режимы управления в этом изменении не реализуются (заготовка под F06)

## Нефункциональные требования
- Среда: MentorPi T1, наш контур; штатный драйвер шасси без учебных игр Hiwonder; тип машины `MentorPi_Tank`
- Стек прикладных нод — C++; статус контура и шасси — в консольной утилите на хосте
- Окно ожидания команды на входе адаптера — параметр `cmd_timeout_ms` (по умолчанию 100), не продуктовый SLA
- Физическая остановка — аппаратный halt шасси, не факт публикации нулевого Twist
- Не интерпретируем лидар. Не второй источник команд на шасси из следования
- Робота в движение приводит строго пользователь; агент и автоматизация этого не делают
- Карта, навигация, MQTT, голос и ручной пульт в это изменение не входят
